## From Concept to Proof

In January I wrote about [ontologies for vendor-agnostic observability migration](/posts/observability-ontologies/)—the idea that a canonical semantic layer could bridge the conceptual gaps between platforms. That post was theory. This one is about what happened when we built it and pointed it at real infrastructure.

The short version: we now have autonomous, AI-driven migration of dashboards and alert rules across three observability stacks—ELK (Elasticsearch/Kibana), LGTM (Loki/Grafana/Tempo/Mimir), and Dash0—using derived ontological mappings that an AI agent traverses at runtime. Not scripts. Not templates. An agent that reads a source dashboard, understands what each panel *means*, and rebuilds it idiomatically on the target platform.

The demo environment is a multi-cluster k3d setup running the OpenTelemetry Demo application, with identical instrumentation feeding all three stacks simultaneously. Same traces, same spans, same services. Three completely different ways of storing and querying them.

## The Derived Ontology

The original post described three components: a canonical model, platform mappings, and gap analysis. What we actually built looks slightly different—and the difference matters.

Rather than a static canonical model, we derived the ontology empirically. We stood up all three platforms against the same OTel data, then systematically mapped how each one represents the same underlying reality. The ontology isn't an abstract schema—it's a set of concrete translation rules extracted from observation.

Take something as simple as "show me the error rate by service." Three platforms, three completely different expressions of the same concept:

**Kibana (KQL + Lens aggregations):** A `count` operation type on an `otel-traces*` data view with a filter column where `span.status.code: 2`, broken down by a `terms` column on `Resource.service.name`.

**Grafana (PromQL against Mimir span metrics):** `sum by (service) (rate(traces_spanmetrics_calls_total{status_code="STATUS_CODE_ERROR"}[5m]))`. Note `service` not `service_name`, and `STATUS_CODE_ERROR` in SCREAMING_CASE.

**Dash0 (PromQL against OTel synthetic metrics):** `sum by (service_name) (rate({__name__="dash0.spans", otel_span_status_code="Error"}[$__rate_interval]))`. Note `service_name`, Title Case `"Error"`, the `__name__` selector syntax, and mandatory `$__rate_interval`.

Same intent. Three different metric names, label keys, label values, query languages, and structural conventions. A syntactic converter would need to handle each pair independently—six translation paths for three platforms. The ontology reduces this to three mappings against a canonical concept: "error rate grouped by service identity."

## What the Mapping Actually Looks Like

The derived ontology isn't a single document. It's a layered system of translation tables that an AI agent consults during migration. Here's what we found we needed:

**Metric identity mapping.** The same underlying data (OTel spans) surfaces as completely different metric names across platforms. Kibana doesn't have "metrics" at all—it queries raw span documents. Grafana's Mimir has `traces_spanmetrics_calls_total` generated by Tempo's span metrics processor. Dash0 synthesizes `{__name__="dash0.spans"}` at query time. Three paradigms: document store, derived counter, synthetic metric.

**Label key mapping.** The service that emitted a span is `Resource.service.name` in Elasticsearch documents, `service` in Mimir span metrics labels, and `service_name` in Dash0. The `service` → `service_name` mapping between Grafana and Dash0 turned out to be the single most common migration error in testing—easy to miss, silent failure.

**Label value mapping.** OTel span status codes appear as integer `2` in Elasticsearch, `STATUS_CODE_ERROR` in Mimir, and `"Error"` (Title Case) in Dash0. Wrong case returns zero results with no error. This is the kind of thing that burns hours in a manual migration and takes seconds to encode in an ontology.

**Structural mapping.** Kibana Lens packs visualization config, query logic, and column definitions into a deeply nested JSON structure with layer IDs and operation types. Grafana uses flat PromQL strings with `gridPos` on each panel. Dash0 uses Perses CRDs with separate `panels[]` and `layouts[]` arrays, grid items referencing panels by index. The AI needs to understand all three structural idioms to translate between them.

**Query pattern mapping.** `increase(...[1h])` is idiomatic Grafana but invalid in Dash0's Perses context—you need `rate(...[$__rate_interval]) * 3600`. `count` in Kibana Lens is a document aggregation; in PromQL it's an entirely different operation. `topk()` works fine in Grafana but breaks Dash0 panels when the inner query returns no series.

## Gap Analysis in Practice

The original post predicted that gap detection would be the killer feature. It is.

When migrating a Kibana dashboard that breaks spans down by `span.name` (operation name), the ontology flags: "span name is not available as a PromQL label in Dash0—too-high cardinality. Substitute with `http_route` or `rpc_method` depending on protocol." The agent doesn't silently drop the panel or generate a broken query. It makes an informed substitution and documents the change.

Similarly, Grafana's service graph metrics (`traces_service_graph_request_total` with `client`/`server` labels) have no equivalent in Dash0. The ontology maps this to RPC service/method groupings as the closest available approximation, and the gap is documented in the migration output.

Some gaps we discovered weren't in the ontology theory at all—they're API-level behaviors that only surface through empirical testing:

Dash0's `dashboards_create` API silently drops the `layouts` field. You must immediately follow creation with an update call containing the same payload. Without this, you get panel titles but empty tiles. No error, no warning. This took real debugging hours to discover and is now encoded in the migration skill so the agent handles it automatically every time.

Dash0's check rule API uses `otel_metric_name` as the metric selector—not `__name__`. Dashboard PromQL uses `__name__`. Same platform, two different selector syntaxes for the same underlying metric. The ontology captures this distinction.

Status code values in check rules are `"ERROR"` (uppercase), while in dashboard PromQL they're `"Error"` (Title Case). Same label, same platform, different casing depending on context.

## The Agent Architecture

The migration isn't a script. It's an AI agent equipped with MCP (Model Context Protocol) servers for each platform—Kibana, Elasticsearch, Grafana, and Dash0—plus the derived ontology encoded as structured documentation the agent reads before executing.

The workflow for a Kibana → Dash0 dashboard migration:

The agent lists source dashboards via `kibana_dashboards_list`, presents options, and extracts the selected dashboard's full definition. It resolves data views to understand whether panels query spans or logs. Then—critically—it samples live data from the Dash0 environment via `dash0_spans_query` to confirm which labels actually exist in the target before building any panels.

For each Kibana Lens panel, the agent reads the visualization type (XY, pie, metric, table), the operation types (count, average, percentile, terms), the source fields, and any filters. It maps each element through the ontology: Lens `lnsXY` becomes `TimeSeriesChart`, a `count` operation on traces becomes `sum(rate({__name__="dash0.spans"}[$__rate_interval]))`, a `terms` breakdown on `service.name` becomes a `by (service_name)` clause.

The agent assembles the Perses CRD, handles the two-step create-then-update dance, and verifies the result. If panels show "no data," it can query Dash0's live span data to diagnose the issue—wrong label name, wrong case, missing filter—and fix it autonomously.

The same architecture handles Grafana → Dash0 with different translation tables. The LGTM metric names, label keys, and query patterns map through the same canonical concepts to different Dash0 expressions.

## What We Learned

**The ontology is never complete on the first pass.** We started with theoretical mappings and refined them through actual migration attempts. Every "no data" panel in the target platform exposed a mapping gap we hadn't anticipated. The 21 "hard-won lessons" documented in our migration skills are battle scars from this process.

**Label cardinality determines what's possible.** High-cardinality fields like span name and span kind are available in Kibana (document-level queries) but absent from PromQL-based platforms where they'd create metric explosion. The ontology must encode these availability boundaries, not just name mappings.

**API behavior matters as much as data model.** The `layouts` silently dropping, the `__name__` vs `otel_metric_name` split, the case sensitivity of status code values—these are implementation details that no theoretical ontology would predict. They only emerge from empirical testing and must be captured for autonomous operation.

**Log severity is sparser than you expect.** Many services write raw stdout logs without OTel severity metadata. A dashboard that segments logs by severity will show nothing for most services. The ontology now defaults to total log volume by service, using severity breakdowns only when confirmed present in the target environment.

**The two-platform problem is deceptive.** Going from Kibana to Dash0 requires one mapping. Adding Grafana as a source requires a second, largely independent mapping—the LGTM stack's data model differs from both ELK and Dash0. But once you have both, you also implicitly have Kibana → Grafana (which we built separately and validated). The ontology's value compounds as platforms are added.

## What This Means for Observability Consulting

Traditional migration engagements rely on senior engineers manually inspecting source configurations, understanding intent, and rebuilding in the target platform. It works, but it's slow and the quality depends entirely on who's doing the work.

With the derived ontology and agent architecture, the mechanical translation is automated. The 22-panel dashboard migration that would take a consultant a day completes in minutes. The consultant's expertise focuses on the gaps—the panels that *can't* translate cleanly, the architectural decisions about what to substitute, the trade-offs between fidelity and capability.

This isn't "AI replaces the consultant." It's "AI handles the conversion work so the consultant focuses on the decisions that actually require judgment." The ontology surfaces those decisions explicitly rather than leaving them buried in implementation details that might not be discovered until production.

The migration skills and ontological mappings are living documents. Every new engagement, every new platform version, every edge case feeds back into the system. The agent gets better at migration the same way a consulting team builds institutional knowledge—except the knowledge is encoded, reproducible, and doesn't walk out the door.
